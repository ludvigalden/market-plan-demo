# Market Plan Desk

A campaign planning tool for a fictional multi-market consumer brand,
"Demo Brand". A planner creates a global campaign, assigns local markets,
sees each market's public holidays and the clashes they cause, and reviews
AI-drafted local adaptations. Nothing changes until the planner accepts a
suggestion, and every decision is written to an audit log.

All brand, campaign and budget data in this repository is fictional. Market
codes are real ISO country codes, because the holiday data is real public
data.

## Architecture

```text
browser ── React SPA (static files served by the API)
                │
             FastAPI ─┬─ SQLAlchemy 2 (async) ── PostgreSQL
                      ├─ httpx ── Nager.Date holidays (cached)
                      └─ AI provider seam ── stub | Foundry
```

- `api/`: FastAPI, Pydantic v2, SQLAlchemy 2 with asyncpg, Alembic.
  Errors share one JSON body (`code`, `message`, `request_id`) and every
  response carries an `X-Request-ID`.
- `api/migrations/`: four Alembic revisions, each with a working
  downgrade. The plan `version` column is added as an expand step:
  nullable with a server default, backfilled, then made `NOT NULL`.
- `contracts/openapi.json`: the API contract, exported from the app with
  stable operation ids.
- `web/`: React and TypeScript on Vite. `src/api/schema.d.ts` is generated
  from the contract by openapi-typescript and used through openapi-fetch,
  so a contract change that breaks the client fails the type check.
- `eval/`: a golden set and a deterministic grader for the AI step.
- `Dockerfile`: one image that builds the SPA and serves it from the API.

## How the AI is constrained

- Deterministic code finds the clashes (a holiday on the launch day, on
  the end day, or inside the plan window). The model is only asked what to
  do about them.
- The model receives the retrieved facts (plan dates, flagged holidays,
  campaign window) and must answer in a JSON schema with a fixed action set:
  `shift_start`, `shift_end`, `note_messaging`, `no_change`. The schema has
  no budget field; budget figures come from the database only.
- A server-side validator drops any suggestion that names a market or a
  flag date that was not in the input, moves a date outside the campaign
  window or onto another holiday, or uses a field outside the schema. The
  response reports how many were dropped and why.
- Suggestions are stored with the model deployment and prompt version.
  Accepting one updates the market plan under optimistic concurrency: the
  request carries the plan version the planner saw, and a stale version
  returns 409.
- `AI_PROVIDER=stub` (the default) answers deterministically from the
  flags, so tests and the eval run without a cloud dependency.
  `AI_PROVIDER=foundry` calls a Microsoft Foundry project through
  `azure-ai-projects` with Entra ID authentication (`DefaultAzureCredential`)
  and structured output.

## Run locally

Requirements: Docker, [uv](https://docs.astral.sh/uv/), Node.js 24.

```sh
docker compose up -d --wait            # PostgreSQL on 127.0.0.1:55432
cd api
uv sync
uv run alembic upgrade head
uv run uvicorn plandesk.main:app --port 8000
```

In a second terminal:

```sh
cd web
npm ci
npm run dev                             # http://localhost:5173, proxies /api
```

Or run the single image against the compose database:

```sh
docker build -t market-plan-desk .
docker run --rm --network host \
  -e DATABASE_URL=postgresql+asyncpg://plandesk@127.0.0.1:55432/plandesk \
  market-plan-desk                     # http://localhost:8000
```

To use Microsoft Foundry instead of the stub, sign in with `az login` and
set `AI_PROVIDER=foundry`, `FOUNDRY_PROJECT_ENDPOINT` and
`FOUNDRY_MODEL_DEPLOYMENT` (see `.env.example`).

## Azure

Terraform in `infra/terraform` provisions the Azure deployment in two roots.

- `bootstrap/` holds the Terraform state account, the resource group, and
  the deploy identity. GitHub Actions signs in as that identity over OpenID
  Connect; it trusts the `production` environment of this repository in
  both subject forms GitHub issues: by name and by numeric owner and
  repository IDs.
- `main/` holds the app:
  - Container Apps on the Consumption plan, scaled to zero when idle;
  - a Basic container registry, pulled with the app's managed identity;
  - PostgreSQL Flexible Server, Burstable B1ms. The connection string is a
    container app secret generated by Terraform. The server is in North
    Europe because Sweden Central refuses the burstable SKU for this
    subscription;
  - a Microsoft Foundry resource and project with a `gpt-4.1-mini`
    deployment (EU data zone). The app calls it with its managed identity
    (the Foundry User role). Key authentication is disabled;
  - Log Analytics with a 0.1 GB daily cap.

Both roots keep their state in the bootstrap account. Pass its names with
`-backend-config`:

```sh
cd infra/terraform/main
terraform init -backend-config=resource_group_name=<prefix>-tfstate \
  -backend-config=storage_account_name=<prefix>tfstate
terraform apply   # prefix, cd_principal_object_id, owner_principal_object_id
```

`.github/workflows/deploy.yml` runs on every push to `main`:

1. Builds the image and pushes it to the registry.
2. Runs `eval/run.py` against the live Foundry deployment. Any failed case
   stops the rollout.
3. Points the container app at the new image. Migrations run before the
   server starts.
4. Waits until `/healthz` reports the database and the Foundry provider on
   the new image.
5. Drives the primary journey in headless Chromium with
   `tools/smoke/smoke.mjs`. The journey covers computed styles, a new
   campaign, markets, live holidays, Foundry suggestions, accepting one,
   and checking after a reload that it persisted.

The workflow reads its settings from variables on the `production`
environment and holds no secrets.

To remove everything, run `terraform destroy` in `main/`, then in
`bootstrap/`.

## Claude Code plugin

`plugin/` is a Claude Code plugin that brings the plan desk into a coding
session. It reads campaigns and proposes adaptations; it cannot accept or
reject a suggestion. Those decisions stay with the planner in the web app.

- `/plan-desk list` lists campaigns.
- `/plan-desk show <campaign>` prints each market's dates, holiday clashes
  and pending suggestions, and opens a side pane with the same view.
  `<campaign>` is an id, an id prefix or a word of the name.
- `/plan-desk suggest <campaign> <market>` drafts adaptations for one
  market and prints them, unaccepted.
- The `plan-desk` skill tells Claude how to use the command when you ask
  about a campaign.

Load it for one session (Claude Code 2.1.317 or later):

```sh
claude --plugin-dir plugin
```

The `apiBaseUrl` option defaults to the Azure deployment. To use a local
API on port 8000, set it in `/config`, or in settings:

```json
{
  "pluginConfigs": {
    "plan-desk": { "options": { "apiBaseUrl": "http://127.0.0.1:8000" } }
  }
}
```

The app scales to zero when idle, so the first call can take about 30
seconds. A call that times out or meets a 502 or 503 says the app may be
waking up.

The hooks run inside Claude Code with no Node runtime, so
`plugin/hooks/client.ts` is a small typed wrapper over the host's fetch,
keyed on `plugin/generated/schema.d.ts`. That file is generated from the
same contract as the web client.

```sh
claude plugin validate plugin
claude plugin test plugin            # formatter, parser, client and command tests
cd web && npm run typecheck:plugin   # needs the API types Claude Code writes
                                     # to plugin/.claude-plugin/types on load
```
